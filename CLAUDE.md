# codeviz

A prototype: code search and, later, visualization and clustering for C/C++ repos, built on clangd. Nothing from this tool goes into the repo it reads.

## Status (2026-10-09)
* Done: the server, the clangd client, the symbol table, and three views behind a hideable sidebar (Ctrl+B):
  * Workspace (first in the sidebar, the landing page; `--diff` and `--cluster` switch to Clusters): the index status (symbol count, and a progress bar only while the symbol pass or clangd's background index runs) and the repo form (repo, compile db, a collapsible folder tree with tri-state boxes, file counts and weight bars, External headers: the include folders outside the repo that the compile db names, such as a library in the Nix store, with header counts, the selected total, Save and index). Clicking the repo name in the header opens it.
  * Settings (bottom of the sidebar): program settings in `$XDG_CONFIG_HOME/codeviz/settings.json` (`src/main/settings.ts`, `GET|POST /api/settings`), saved on each change. Transparent window (the desktop shows through; the shell at Shell opacity, default 0.75, and the canvas black at Canvas opacity, default 0.5; Electron fixes transparency at window creation, so main.ts makes a new window in place when it changes), dot grid, boxes per cluster (600), files and changes per commit view (400, 800), canvas cache MB (384).
  * Back and forward (`nav.js`): mouse buttons 4 and 5 or Alt+Left/Right. A view change, a new or picked tab, and a camera glide (a link, numpad .) each push the place first (view, tab, camera); calls in one tick count as one.
  * The sidebar's collapse arrow sits at its top right, and in the view's top left corner while it is hidden (Ctrl+B too).
  * Markdown docs: a `.md` path in a commit view (the card, the added/deleted lists, a file box's header) opens a doc tab: the file rendered at that commit (the base for a deleted file, disk for the working tree), `GET /api/file?path=&rev=[&links=1]`. `markdown.js` wraps `vendor/marked.min.js` (marked 18, copied from hexcode): raw HTML stays text, only web links and images load, repo-relative links open as docs at the same revision, C/C++ fences use `code.js` colours.
  * Cluster tabs: press to open, drag to reorder, middle-click to close, right-click for close / to the left / to the right / others / all (`showMenu` in `dom.js`).
  * Symbol search: every function, method, struct, class, union, enum and typedef whose name contains the query.
  * Clusters: click a symbol and a pannable 2D world shows it and everything related to it as outlined, highlighted source boxes with their comments. Click a name in a box for a new tab; shift-click adds that symbol's cluster to this tab, outside the others, and the camera glides there. Click a box to select it; numpad `.` frames the selection (or the focus), Home or F fits everything (Blender's keys).
  * Changes: the working tree and recent commits (refreshed on window focus and every 10 s while shown), plus a rev box (`sha`, `A..B`, `main...branch` for a PR). One opens as a commit tab in Clusters: a summary card (message, files with churn bars that jump to their box), a "Deleted N files" box listing the symbols that went with them, an "Added N files" box, and one box per changed function, type or stretch of code outside symbols, with the whole block before and after side by side, each top-aligned like a cluster box (no folds, no alignment gaps; changed lines tinted). An added symbol's before side is a slim "new" column; a deleted one's after side says "deleted". Non-code files of one extension beyond 6 collapse into one list box. Layouts: Biggest changes (default), By change, By file, By folder. Names in a commit box open symbol clusters as usual. The intended use: open an agent's commit or PR and pan around it to understand it.
* UX decided (2026-10-09): a type's cluster is its API surface (signatures that name it, records with a field of it, typedefs of it). A function's cluster is its signature's types plus direct callers and callees. Layouts: by file, by folder, by kind, by relation, and Affinity (Claude's pick: a force layout).
* Next: try the commit view. The cluster view's open questions: the 600-box cap (a core type can have over 1000 related), text selection (dragging pans everywhere), drawing edges between boxes.
* Nested unnamed records (`(anonymous struct)`) are left out of clusters; they show inside their parent's block.

## Build & run
* Every command runs in the flake: `nix develop path:. --command <cmd>`. The flake pins nixpkgs: node 22.22, electron 38.8.4, clangd 21.1.8, tsc 5.9.3, python 3.13 (for ad hoc checks, such as parsing `curl` output). Never use npm's electron binary; `ELECTRON_SKIP_BINARY_DOWNLOAD=1` is set, and the npm package is there for types only (keep its version equal to the flake's electron). Use `tsc`, never `npx tsc` (that fetches an unrelated package).
* Build: `nix develop path:. --command tsc -p .` (writes `dist/main/`). Only `src/main/` is TypeScript; `src/ui/` is plain JS with no build step and no type check.
* Run: `scripts/run.sh [flags]` from anywhere. It enters the flake if needed, builds, then opens the last workspace on the Workspace page. `nix develop path:. --command npm start -- [flags]` does the same; `npm start` runs `$CODEVIZ_ELECTRON`, which only the flake's shell sets.
* Package: `scripts/package.sh` runs `nix build` on the flake's `packages.default` (`buildNpmPackage`) and links `./result`. `result/bin/codeviz [flags]` is nixpkgs' electron with clangd on PATH and the app in `lib/codeviz` (dist, src/ui, runtime node_modules, about 600 KB); it shares the workspaces and caches in `~/.local/share/codeviz`. `nix profile add path:.` installs it (`nix profile upgrade codeviz` picks up new commits). The package ships `share/applications/codeviz.desktop` and the icon `assets/codeviz.svg` as `share/icons/hicolor/scalable/apps/codeviz.svg`; main.ts sets the window class to `codeviz` to match the entry's StartupWMClass. When `package-lock.json` changes, update `npmDepsHash` in `flake.nix` (build with a wrong hash, copy the "got:" one).
* Pass flags after `--`: `nix develop path:. --command npm start -- --shot .cache/shots/vec.png --query vec`.
* Probe clangd: `nix develop path:. --command npm run probe -- [--workspace <repo>] [--depth <n>] <file>...` prints the `documentSymbol` tree and each USR (`scripts/probe.ts`, built by `tsconfig.scripts.json` into `dist/scripts/`). It uses the saved workspace and the same clangd index as the app. Extend it to try other clangd requests (call hierarchy, references) before building on them.
* Flags (`src/main/main.ts`):
  * `--workspace <repo> --roots src,third_party/lib [--compile-db <path>]` opens a repo with those folders and saves the config. Without `--compile-db` (and no saved one), it picks the compile db with the most entries under those folders; the Workspace page lists them best first too.
  * `--diff <rev>` opens a commit tab (`worktree` for uncommitted changes). Only one app runs at a time (except `--shot`): a second `scripts/run.sh --diff <rev>` opens the tab in the running app and focuses it. So an agent that finished a commit can show it with `scripts/run.sh --diff HEAD`. The rev is read in the open workspace's repo.
  * `--port <n>` serves on a fixed port, so `curl localhost:<n>/api/search?q=vec` works while the app runs. Without it the port is random; a running app (not `--shot`) writes `{port, pid}` to `$XDG_STATE_HOME/codeviz/server.json` (default `~/.local/state/codeviz/server.json`) and removes it on quit.
  * `--help`/`-h` prints the flags and exits; an unknown flag prints an error and exits with 1 (`parseArgs`, strict only for the process's own argv, so Chromium switches such as `--no-sandbox` pass).
  * `--shot <png>` renders hidden, waits for the symbol pass, saves a screenshot and quits. Look at every UI change this way (keep shots in `.cache/shots/`). The page's console prints as `[page] ...`. With it:
    * `--query <text>` types into Symbol search.
    * `--cluster <name> [--layout file|folder|kind|relation|affinity]` opens that symbol's cluster.
    * `--diff <rev> [--layout impact|change|diff-file|diff-folder]` opens a commit tab.
    * `--eval <js>` runs JS in the page last, awaited, to drive the UI (dispatch clicks, wait, click Fit). `window.codeviz.boxes()` lists the box rects (check overlaps); `window.codeviz.look(name, zoom)` selects a box and shows its top left at exactly that zoom; `await window.codeviz.ready()` waits until every box in view is drawn (do that before the shot ends); `window.codeviz.benchZoom(n)` times a zoom from fit-all to 1.5x.
    * The hidden window gets `requestAnimationFrame` at about 1 Hz (no compositor), so animations crawl and frame timing means nothing there; time paint work with `benchZoom`, and judge smoothness in a visible window.

## Architecture
* Electron owns everything. Its main process runs the HTTP server and spawns clangd as a child process. Closing the app stops both. The UI is plain HTML and JS served over HTTP from `src/ui/`. It loads in a browser too.
* `src/main/workspace.ts`: workspace configs in `~/.local/share/codeviz/workspaces.json`, one per repo: root, compile db, chosen folders, chosen externals. An external (`externalCandidates`, from the `-I`/`-isystem`/`-iquote`/`-idirafter` flags) is saved by a key without the store hash and version (`sdl3-dev/include`), so a nixpkgs update keeps it; only its headers are read. Its files' location paths start with its label (`sdl3-3.4.0-dev/include/SDL3/SDL_gpu.h`); `SymbolIndex.rel`/`abs` map them. `writeFilteredCdb` writes a compile db with only the chosen folders into `~/.local/share/codeviz/<name>-<hash>/`. clangd's background index (`.cache/clangd/`) and our `symbols.json` live there too, never in the target repo.
* `src/main/headers.ts`: compile commands for headers, written into the filtered compile db. Many headers are not self-contained (Jolt's need `Jolt.h` first) and parse as garbage alone. Each header gets the command of a source that reaches it, as `-x c-header`/`c++-header`, with `-include` for everything included before it along the chain (read as text; includes under `#if` are followed but not put in front). Of all chains, the shortest context wins, so a self-contained header gets none. About 0.7 s for a repo of 2235 headers (1595 get an entry; the rest no source reaches). The symbol collector also walks into macro expansions outside records (`JPH_NAMESPACE_BEGIN`), so Jolt names come out as `JPH::...`.
* `src/main/clangd.ts`: clangd over LSP (vscode-jsonrpc) with `--background-index --query-driver=** --limit-results=0`. Two processes share the compile db: the main one (background index, `-j` half the cores; call hierarchy, diffs, warm) and a reader for the symbol pass (no index, every core, as many files in flight). Each gets `XDG_CONFIG_HOME` pointed at `<workspace dir>/config`, so the user's clangd config does not apply; ours turns off unused/missing-include checks and has the background index skip header entries (their symbols reach it through the sources that include them; checked: header shards are still written). `fileSymbols` opens a file, asks for `documentSymbol`, asks `textDocument/symbolInfo` (a clangd extension) for each symbol's USR, then closes the file.
* `src/main/index.ts`: `SymbolIndex`. It walks every C/C++ file under the chosen folders and reads only files whose mtime or size changed since the cache. It merges the results by USR, so the header declaration and the `.c` definition become one symbol with several locations. A location is a definition when there is a `{` in its range. Search is a case-insensitive substring match, on the qualified name when the query has `::`. Ranking: exact, prefix, word start (`_`, `:`, camel step), substring, then a substring with every `_` ignored (`type_db` finds `typedb_t`), then shorter names first. The lowercased keys are made per symbol on first search.
  * Each cached symbol keeps `refs`: the identifiers its interface mentions (a function's signature, a record's field types, a typedef's text). `usersOf(name)` is the reverse, the API surface of a type.
  * `calls(sym)` asks clangd's call hierarchy at the definition and maps the answers back to symbols by file and line.
  * clangd loads its index from disk only when it first opens a file, and call hierarchy answers are empty until then. `warm()` opens one file at start for that reason.
* `src/main/cluster.ts`: `buildCluster` returns the related symbols with a relation (`self`, `returns`, `takes`, `field`, `alias`, `type`, `caller`, `callee`). Each gets a source block (the definition, else the first declaration) with the touching comments above it, trailing comments that a blank line closes, tabs expanded and shared indentation removed. Over 600 items the rarer relations are kept first. `links` maps each identifier in the blocks to a symbol, so the UI can make names clickable (by name; good for C, ambiguous for C++ overloads).
* `src/main/diff.ts`: `buildDiff(index, rev)`. Git gives the changed files (`--raw -M`, plus untracked files for the working tree) and `-U0` hunks. Both sides of each C/C++ file go through clangd's `documentSymbol` (the old text is sent under the real path; `clangd.ts` locks each file so the two opens don't interleave). Symbols match by kind group, container and name; a match whose block text differs is "modified", one present on one side only is "added" or "deleted", and a deleted and an added symbol with the same key in different files is "moved". Changed lines outside every symbol become "outside symbols" entries; non-code files are one entry each. Before and after are aligned line by line (LCS). Symbols in deleted files are only listed, not shown as entries. Files come from `git diff --raw`; a submodule whose commit moved (mode 160000) is diffed inside between its two commits (its working tree for `worktree`), recursively, and its files join the list under its path; each `FileChange.git` says which repo and revs to read. The card lists each submodule's range and commits; when its checkout lacks a commit, the pointer change stays one file entry. `fileAt` reads a submodule file at the submodule's commit in the given rev. Caps: 400 files, 800 entries, 300 lines per file entry. `recentCommits` feeds the Changes view.
* The projector: `POST /api/view {cmd, repo?, newTab?, focus?, ...}` (`view()` in `main.ts`, through `ServerHooks.view`). Commands: `diff {rev, layout?, symbol?, path?}` (with `symbol` and/or `path`, `openSymbolDiff` in `clusters.js` shows only the matching changes, before | after, stacked in a frame named after the commit; a plain name also matches `ns::name`; no match is an error listing up to 30 changed symbols), `file {path, line?, endLine?}` (a repo-relative or absolute path inside the workspace; one box from `fileBox` in `diffboxes.js`, C/C++ coloured with clickable names from `/api/file?links=1`, the range tinted `markBg` and framed; files over 4000 lines show the 4000 around the range; `.md` opens as a doc tab), `symbol {name, layout?}`, `search {query}`, `shot {path?}` (`capturePage`, default `~/.cache/codeviz/shots/`), `state`. Display commands run `window.codeviz.project()` in the page, which opens views with `{projector: true}`: they replace the one ▶ tab (`pushTab` in `clusters.js`), and `newTab` keeps the old one as a plain tab. `repo` switches to that repo's saved workspace, or fails. Symbol commands wait up to 180 s for the symbol pass. The window is shown with `showInactive` unless `focus`. Answers are `{ok: true, ...}` or `{error}` with 400/404/409/503.
* `src/main/mcp.ts`: the stdio MCP server (`codeviz-mcp` in the package, `scripts/mcp.sh` or `npm run mcp` in a checkout; no dependencies). Newline-delimited JSON-RPC 2.0: `initialize` (echoes the client's protocol version), `ping`, `tools/list`, `tools/call`; tool calls run one at a time. Tools: `open` (spawns `$CODEVIZ_BIN`, the package's `bin/codeviz`, the checkout's `scripts/run.sh`, or `codeviz` on PATH, detached with `--workspace <repo>`, and waits up to 60 s), `show_diff`, `show_file`, `show_symbol`, `search`, `screenshot` (an MCP image block plus the path), `state`. Each forwards to `/api/view` with `repo` = the git toplevel of its cwd (`INIT_CWD` under npm). With no app, every tool but `open` and `state` answers "codeviz is not running; call open or start it from the launcher".
* `src/main/blocks.ts`: source blocks with their comments (shared by clusters and diffs).
* `src/main/http.ts`: `GET /api/state`, `GET /api/search?q=&kinds=&limit=`, `GET /api/cluster?id=|name=`, `GET /api/commits?limit=`, `GET /api/diff?rev=`, `GET /api/file?path=&rev=&links=`, `GET|POST /api/settings`, `POST /api/view` (the projector), `POST /api/workspace/inspect|open`, `POST /api/rescan`, `POST /api/pick-folder` (Electron's native dialog).
* UI (`src/ui/`): ES modules, no build step. Each view has its own JS and CSS in `views/`:
  * `app.js`: the shell. Status polling, the sidebar, and the `window.codeviz` hooks that `--shot` uses.
  * `dom.js`: shared helpers (`el`, `api`, `highlight`, `showMenu`).
  * `views/workspace.js`: the Workspace view.
  * `views/search.js`: Symbol search. Clicking a result opens its cluster.
  * `views/changes.js`: the Changes list. Clicking opens a commit tab.
  * `diffboxes.js`: turns a diff into boxes the renderer draws: a box can carry its own header (chip, name, tags) and rows of tokens with background bands, instead of a code block. `goto:<box id>` links glide to another box.
  * `views/clusters.js`: tabs, clusters, box sizes from the monospace metrics, selection, and the camera (drag to pan, wheel to zoom at the cursor; moves ease with the zoom in log space). Appended clusters are laid out on their own, then placed with `placeNear` next to the clicked box.
  * `render.js`: the world is one canvas. Each box is drawn per zoom level (2x, 1, 1/2 ... 1/16, picked from zoom x devicePixelRatio; the levels act as mips) as 512 px tiles in cached OffscreenCanvases, LRU within 384 MB, so a huge box is as sharp as a small one and only its tiles in view are drawn. Inner tiles overlap their neighbour by 1 px so no seam shows. A frame only draws cached tiles in view; missing ones are drawn about 10 ms per frame, nearest the middle first, and until then their area shows other levels' cached tiles (coarser first). At 1/8 and under, code is minimap bars. Under 0.35 zoom names are drawn over the boxes and group labels grow, capped to their outline's width. Clicks hit-test the monospace grid of the tokenized lines. Boxes have a header bar in their colour (kind in italics) and sharp corners; the canvas is black with a dot grid. Measured on a 600-box cluster: paint under 1 ms of CPU, about 0.3 ms per bitmap, 100–150 MB cached.
  * `code.js`: a C/C++ tokenizer. It splits a block into lines of coloured tokens; identifiers that name a symbol carry its id.
  * `layout.js`: the layouts. The commit layouts pack groups in rank order with a bottom-left skyline (biggest first), so the largest changes sit top left beside the card. Groups are packed in newspaper columns (keeps line order) or in shelves. `placeNear` puts a rect against existing rects, nearest a target, with vertical distance counted double. Affinity uses springs between boxes that name each other's symbols, a pull to the centre, and push-apart of overlaps (sweep and prune), then moves any box that still overlaps to the nearest free spot, so it never overlaps.
* `SymbolIndex.scan()` runs one pass at a time. Stale files are read biggest first, so no large file runs alone at the end. A rescan sent during a pass queues one more pass after it. A pass re-reads only files whose mtime or size changed (a no-op pass is a walk and a stat, about 20 ms for 4041 files). The UI asks for one on window focus, and `/api/cluster` runs one before it builds (`fresh()`), so blocks never cut today's file with yesterday's lines.
* `symbols.json` has a `CACHE_VERSION` (`src/main/index.ts`). Bump it when `RawSym` changes; old caches are then thrown away and read again.

## Indexing cost (measured 2026-10-09, under load)
* clangd spends about 1.3 CPU-s per file of the test repo, nearly all in the preamble (every included header parsed and serialized, 33 MB for one large C++ file: preamble 1.05 s, AST 0.14 s). So per-file options barely move it: unused-include checks off saved about 2%; `-Xclang -skip-function-bodies` (needs a brace scanner for definition ends, 99.8% right) saved about 9% of the AST part, within noise, and was dropped. Preambles are not shared across files. symbolInfo calls are under 1% of the time.
* What scales it: cores (the reader uses all of them) and less competing work (the background index no longer indexes the 1595 header entries as their own files, about 55% of its entries).

* No tests. To check a change, use `--shot` and `curl` against `--port`.

## Facts measured on a test repo (2026-10-08)
* About 1040 files and 15,638 symbols. The first pass takes about 45 s on 32 cores (with its third-party libraries and the header commands, 4130 files took 7m42s, clangd's background index running alongside); a restart loads from the cache at once. The cache is 42 MB, most of it clangd's index.
* A search takes about 1 ms (the first one about 25 ms, while it builds the keys). For one sampled query, grep found no name that the index misses.
* Clusters (2026-10-09): the most used core type has 1245 related symbols (563 of the 600 kept take it as a parameter), built in about 20 ms, 1 MB of text. A mid-sized type has 139. A function's cluster takes 60–170 ms (clangd).
* Commit view: a commit of 50 files and 104 modified symbols builds in about 5 s, one of 28 files (2 deleted) in about 2 s, a one-symbol commit in 0.25 s. Most of the time is clangd parsing both sides.
* clangd details: a C typedef of a struct appears as a `struct` and a `type alias` with the same USR; they merge into one `struct`. `symbolInfo` on a typedef of a builtin returns the builtin's USR, so those get a synthetic `codeviz:T@` id.

## Ideas for the visualization work (not decided)
* The background index can also answer references and type hierarchy, keyed by the USRs that are already in the table.
* A repo's layers often come from folder names. They are a ready-made clustering signal and a way to check layer rules.
* The include graph comes from the compile db plus clangd.
* No live file watching; files are re-read on window focus and before each cluster.
